# [ENRIQUECIDO] Extender respuesta de GET /position/:id/candidates con id y applicationId

creando_interfaz_gestion_aplicaciones_LTI.md

## 1. Descripción refinada

### Problema a resolver
El endpoint `GET /position/:id/candidates` utiliza el servicio `getCandidatesByPositionService`, el cual **ya devuelve** `id` (candidateId) y `applicationId` en cada objeto candidato (líneas 27-28 de `positionService.ts`). Sin embargo:

1. La **especificación OpenAPI** (`api-spec.yaml`) no documenta estos campos → cualquier consumidor que genere cliente a partir de la spec no los recibirá.
2. Los **tests unitarios** (`positionService.test.ts`, `positionController.test.ts`) no verifican que estos campos estén presentes → el contrato no está validado.
3. Los **tipos de frontend** (`CandidateData` en `frontend/src/types/position.ts`) **ya incluyen** ambos campos (`id`, `applicationId`), pero debe verificarse que no haya mismatch semántico (ej: tipo `number` vs `string`).

### ¿Qué NO incluye este ticket?
- ❌ No cambia lógica de negocio — el servicio ya funciona correctamente.
- ❌ No modifica el frontend — los tipos ya están alineados.
- ❌ No añade nuevos endpoints.

### Impacto downstream
Este cambio es **bloqueante** para el ticket `003-implementar-arrastre-y-actualizacion.md`, que necesita:
- `id` como `draggableId` del `<Draggable>` de react-beautiful-dnd.
- `applicationId` en el payload de `PUT /candidates/:id/stage`.

#### Test 1.3: Verificar valores numéricos correctos para `id` y `applicationId`

```typescript
it('should return id and applicationId as numbers (not strings)', async () => {
  const mockApplications = [
    {
      id: 1,
      positionId: 1,
      candidateId: 1,
      applicationDate: new Date(),
      currentInterviewStep: 1,
      notes: null,
      candidate: { firstName: 'John', lastName: 'Doe' },
      interviewStep: { name: 'Technical Interview' },
      interviews: [{ score: 5 }],
    },
  ];

  jest.spyOn(prisma.application, 'findMany').mockResolvedValue(mockApplications);

  const result = await getCandidatesByPositionService(1);

  expect(typeof result[0].id).toBe('number');
  expect(typeof result[0].applicationId).toBe('number');
  expect(Number.isInteger(result[0].id)).toBe(true);
  expect(Number.isInteger(result[0].applicationId)).toBe(true);
});
```

**Motivación**: El frontend usa `id` como `draggableId` en `<Draggable draggableId={candidate.id}>`. react-beautiful-dnd espera un string, y en React se pasa como `{candidate.id}`, que con `number` se convierte a string automáticamente. Pero si el backend cambiara a devolver string, no habría problema. Lo importante es verificar que el tipo es consistente.

### Escenarios cubiertos por los tests propuestos

| Escenario | ¿Cubierto? | Test |

### Escenarios NO cubiertos (fuera del alcance intencionadamente)

| Escenario | Razón | Acción recomendada |
|---|---|---|
| `app.candidate` es null | Debería ser imposible por FK en BD. Si ocurre, es un bug en datos, no en este endpoint. | Debatir si se añade guardia en el servicio en ticket separado. |
| `app.interviewStep` es null | Ídem. El servicio fallaría con `TypeError: Cannot read properties of null`. | Ticket separado para manejo de datos corruptos. |
| `positionId` no existe (404) | El servicio actualmente lanza un error genérico y el controlador devuelve 500 (no 404). | Esto es un bug preexistente, no relacionado con este ticket. Documentar como deuda técnica. |
| Respuesta vacía (`[]`) | El servicio ya la maneja correctamente (findMany devuelve array vacío). | No requiere test adicional, pero se puede añadir si se desea. |
| Validación de `positionId` no numérico | Express no valida params; `parseInt` devolvería `NaN`. | No es responsabilidad de este ticket. |

### Deuda técnica documentada

El controlador `getCandidatesByPosition` trata todos los errores del servicio como 500, incluso cuando el error es "Position not found" (que debería ser 404). Esto afecta a `getInterviewFlowByPositionService` también, que sí tiene manejo de 404. Este bug **no está en el alcance** de este ticket, pero se recomienda crear un ticket de seguimiento para alinear el manejo de errores entre ambos endpoints.
