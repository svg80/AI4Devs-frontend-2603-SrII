# Extender respuesta de GET /position/:id/candidates con id y applicationId

## Epic
creando_interfaz_gestion_aplicaciones_LTI.md

## Descripción
El endpoint `GET /position/:id/candidates` debe devolver `id` (candidateId) y `applicationId` en cada candidato. Estos campos son necesarios para que el drag & drop (ticket 003) pueda:
- Usar `id` como `draggableId` en `<Draggable draggableId={candidate.id}>`.
- Enviar `applicationId` en el payload de `PUT /candidates/:id`.

La implementación en `positionService.ts` ya devuelve estos campos, pero falta:
1. Actualizar la especificación OpenAPI (`api-spec.yaml`) para documentarlos.
2. Actualizar los tests del backend para verificar que se devuelven correctamente.
3. Verificar que los tipos del frontend (`CandidateData`) están alineados.

## Criterios de aceptación
- [ ] `api-spec.yaml` documenta `id` (type: integer) y `applicationId` (type: integer) en la respuesta 200 de `GET /position/{id}/candidates`.
- [ ] `positionService.test.ts` verifica que cada elemento del array devuelto incluye `id` y `applicationId` con valores correctos.
- [ ] `positionController.test.ts` verifica que la respuesta JSON incluye `id` y `applicationId`.
- [ ] `npm test` en `backend/` pasa sin errores.
- [ ] Los tipos `CandidateData` en `frontend/src/types/position.ts` ya incluyen `id` y `applicationId` (verificar que no hay mismatch).

## Notas técnicas
- El servicio en `backend/src/application/services/positionService.ts:23-29` ya mapea `id: app.candidate.id` y `applicationId: app.id`.
- El tipo `CandidateData` en `frontend/src/types/position.ts:33-39` ya define ambos campos.
- `api-spec.yaml` línea 208-214 es la sección a modificar para añadir `id` y `applicationId`.
- Los tests existentes usan `toEqual` que permite propiedades extra, pero hay que añadir aserciones explícitas para que el contrato quede verificado.
